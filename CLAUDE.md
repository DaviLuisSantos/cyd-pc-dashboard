# CLAUDE.md

Painel do projeto **CYD PC Dashboard** (repo `cyd-pc-dashboard`).

Orientações para agentes trabalhando neste repositório. Respostas e comentários de código em **português**. O README é em inglês (projeto público/portfólio) e a UI do painel é bilíngue (EN / PT-BR via `PANEL_LANG`).

## O que é

Firmware para o **ESP32-2432S028R (Cheap Yellow Display / CYD)** — um painel auxiliar de mesa. Seis telas navegáveis por toque:

- **Relógio** (`screen_clock.h`) — hora/data via NTP. Herança do MVP inicial, não é foco.
- **PC Stats** (`screen_pcstats.h`) — anéis de CPU/RAM, sparkline de histórico da CPU, disco e rede. É o coração do painel.
- **Processos** (`screen_procs.h`) — top 4 processos por CPU (agregados por nome no agente).
- **Rede** (`screen_sysinfo.h`) — ping, uptime, IP público e sparkline de download.
- **Cotações** (`screen_quotes.h`) — até 4 ativos (fiat/cripto) numa moeda base, ambos definidos no `agent/config.json`.
- **YouTube** (`screen_youtube.h`) — inscritos/views/vídeos dos canais configurados no agente (requer API key).

Todas menos o Relógio consultam um agente HTTP (`agent/pc_stats_agent.py`) rodando na máquina local (`/stats`, `/quotes`, `/procs`, `/sysinfo`, `/youtube`).

**GPU não interessa** — o mantenedor pediu explicitamente pra não incluir métricas de GPU no painel.

**Visual: temas de cor (Dracula por padrão), navegação por abas.** Tab bar fixa no topo (34px) com ícones vetoriais (sem bitmap/filesystem); tocar numa aba troca de tela direto — sem mais swipe nas bordas. Ver seção "Tema visual" abaixo.

## Build / gravação

Projeto **PlatformIO** (não Arduino IDE). Ambiente único: `[env:cyd]`.

```
pio run                # compila
pio run -t upload      # compila e grava (upload_speed 921600)
pio device monitor     # serial @ 115200
```

**Depois do primeiro flash com partição OTA, gravar pela rede** (sem botão): `curl -F firmware=@.pio/build/cyd/firmware.bin http://cyd-dashboard.local/api/update` (ou o IP; comando serial `i` mostra). Testar mudanças pela API da interface web (`/api/status`, `/api/settings`, `/api/tab`, `/api/touch`, `/screenshot.bmp`) em vez de pedir pro usuário olhar a tela.

Driver USB da placa: **CH340**. **Gravação nessa placa:** o auto-reset não coloca em download mode (`Wrong boot mode detected (0x13)`) e o `pio run -t upload` ainda desfaz o download mode manual. O que funciona: deixar o esptool esperando com `--before no_reset --connect-attempts 0` (em background) e só então pedir pro usuário segurar BOOT → apertar/soltar RST → soltar BOOT. `pio` não está no PATH: `~/.platformio/penv/Scripts/pio.exe`.

**Release:** tag `vX.Y.Z` → `.github/workflows/release.yml` compila com `-DFW_VERSION`, gera o binário único (`esptool merge_bin`, offset 0x0), cria a GitHub Release e publica `web/index.html` + `manifest.json` + `firmware.bin` + `docs/screenshots/` no GitHub Pages (instalador ESP Web Tools). CI (`.github/workflows/build.yml`) compila o firmware **sem** `user_config.h` (só defaults) e roda pyflakes no agente — qualquer mudança precisa continuar compilando nesse cenário.

## Visão / Roadmap

O objetivo é ser uma **tela auxiliar permanente ao lado do PC**, mostrando informações de relance.

**Foco:** o mantenedor já tem OUTRO dispositivo dedicado a relógio/clima/tempo. Este painel NÃO é sobre isso — ele mostra o que aquele não mostra: dados do PC, mercado e afins. Não priorizar/expandir tela de relógio ou clima aqui (a `screen_clock.h` atual é herança do MVP e pode até sair no futuro).

Direção pretendida (múltiplas telas navegáveis por toque):

- **PC Stats** (`screen_pcstats.h`) — feito com CPU/RAM/disco/rede e temperatura da CPU (GPU continua fora, a pedido do mantenedor).
- **Cotações** (`screen_quotes.h`) — genérico: ativos e moeda base vêm do config do agente.
- Novas telas de coisas úteis de ver de relance, cada uma como um `Screen` habilitável via `ENABLE_SCREEN_*`.

**Decisão de arquitetura para dados externos (cotações):** resolvido — o `pc_stats_agent.py` busca as cotações (AwesomeAPI para fiat, CoinGecko para cripto, ambas via `urllib` da stdlib, sem chave) e expõe em `/quotes`, cacheado em memória e atualizado a cada 60s por uma thread de background. O ESP32 só fala HTTP puro com o agente, nunca HTTPS direto com APIs externas. Faz sentido porque o painel já é "auxiliar ao PC" — só é útil com o PC ligado mesmo.

## Arquitetura

- **Toda a config da TFT_eSPI vem por `build_flags` no `platformio.ini`** — NÃO editar `User_Setup.h` da lib. Display ILI9341 320x240, HSPI. Se mexer em pinos/driver do display, é lá.
- **Dois periféricos SPI distintos**: display no HSPI (**`-DUSE_HSPI_PORT=1`** nos build_flags — sem isso o TFT_eSPI usa VSPI), touch XPT2046 no VSPI (`touchSPI` em `main.cpp`, pinos em `config.h`). Não misturar: com os dois no VSPI a escrita no display funciona (o GPIO matrix replica a saída), mas o `touchSPI.begin()` redireciona o único MISO do periférico pro pino do touch e toda leitura do display (`readRect`, screenshot) volta zerada. `SPI_READ_FREQUENCY` fica em 6MHz: a 20MHz os bytes lidos chegam deslocados 1 bit.
- **Cores invertidas — `tft.invertDisplay(settings.invert)` em `applyDisplaySettings()` (`main.cpp`), logo após `tft.init()` e de novo depois do portal (default `DISPLAY_INVERT` = `true`).** Muitas unidades do CYD (ESP32-2432S028R) mostram cor invertida com `ILI9341_2_DRIVER` (a sequência de init alternativa do driver corrige outros problemas do painel, mas não define a polaridade de inversão). Sintoma sem essa chamada: o fundo escuro do tema (Dracula `#282a36`, quase preto) aparece **branco/cinza-claro** — inverter um RGB565 escuro dá um valor claro, então "fundo branco" com tema escuro configurado é o sinal clássico disso. Se depois de gravar as cores ficarem estranhas na direção oposta (era certo, virou errado), desmarcar *Invert colors* no portal (ou `DISPLAY_INVERT false` no `user_config.h`) — é hardware-dependente, sem como cravar de antemão sem o board físico na mão.
- **Configuração em duas camadas:** `src/config.h` (versionado) tem TODOS os defaults, cada um protegido por `#ifndef`, e inclui `src/user_config.h` via `__has_include` se existir. `user_config.h` é **gitignored** (credenciais WiFi, IP do agente, idioma, TZ, telas) — o usuário copia de `user_config.example.h`. Opção nova = adicionar `#ifndef`/default em `config.h` + linha comentada no `.example.h` + linha na tabela do README. Nunca colocar credencial real em arquivo versionado.
- **`src/i18n.h`** — todos os textos da UI (status, labels, nomes de tela, formato de data) em EN e PT-BR, escolhidos por `PANEL_LANG`. Texto novo na tela vai pra lá nas duas línguas, só ASCII (fontes sem acento).
- **`src/agent_client.h`** — `agent::fetch(tft, "/endpoint", doc)` faz GET + parse JSON e desenha o status dot de erro (sem wifi / agente offline / json inválido); `agent::showOk`/`showStatus` pro rodapé. Telas novas que consomem o agente devem usar isso em vez de repetir `HTTPClient`.
- **Config em runtime (`src/settings.h` + `src/wifi_setup.h`):** IP/porta do agente, fuso, idioma, formato de hora (12/24h) e data, abas (lista/ordem), auto-next, brilho, rotação, inversão de cores e modo noturno ficam no NVS (namespace `cydpc`), editáveis no portal WiFiManager (AP `CYD-Dashboard`, 192.168.4.1) e na interface web pós-boot. Precedência: NVS > `user_config.h` > `config.h`. O portal abre sozinho sem rede salva, ou segurando a tela durante a barrinha do boot (`bootSplashWantsSetup`). WiFi: tenta `WIFI_SSID` de compilação, depois as credenciais salvas pelo WiFiManager, depois o portal. Opção nova = campo em `Settings` + load/save (chave NVS ≤15 chars) + `KEYS`/`setField`/`getField` + entrada em `FIELDS` (`wifi_setup.h`) + campo no formulário de `web_ui.h` + linha na tabela do portal no README. Código novo NUNCA lê `AGENT_HOST`/`TZ_INFO`/`PANEL_LANG`/`AUTO_NEXT_MS`/`BACKLIGHT_LEVEL`/`DISPLAY_*`/`SCREEN_ORDER` direto — usa `settings::get()`; textos via `i18n::tr().X` (idioma é runtime).
- **Comandos seriais (`src/serial_cmds.h`, 115200):** `s` despeja o framebuffer (RGB565 big-endian, protocolo no header), `n` próxima aba, `a` liga/desliga auto-next, `r` apaga o NVS e reinicia, `i` mostra versão/IP/endereço da interface web. `tools/screenshot.py` gera os PNGs de `docs/screenshots/` pela interface web (`--host cyd-dashboard.local --tabs 6 --grid 3` → `tab1..6.png` + `overview.png`; `--themes dracula,nord,... --grid 3` → `themes.png`, voltando pro tema original) ou pela serial (`--port COM3`, abre sem DTR/RTS pra não resetar). **Screenshots públicos: sempre com `tools/demo_agent.py`** no lugar do agente real (dados fictícios em todos os endpoints, processos/canais genéricos, IP público da faixa de documentação 203.0.113.x) e com todas as 6 abas habilitadas (`screens`) — sem dado pessoal na imagem. Conferir os rótulos em inglês: foi assim que apareceu o "subscribers" cortado no YouTube (região dinâmica sobrepondo label estático em smooth font — medir a largura real, a smooth font é mais larga que a font 2).
- **Partições:** `min_spiffs.csv` (2 slots de app de 1.9MB pra OTA; firmware ~1.24MB = 63%). O NVS fica no mesmo offset (0x9000) do `huge_app` antigo, então trocar de partição não perde configuração. Placa com a partição antiga precisa de UM flash por USB pra migrar.
- **Alertas (`src/alerts.h`):** limites `settings.alertCpu/Ram/Disk` (0 = off). `alerts::color()` dá a cor de anel/barra (vermelho ≥ limite, laranja ≥ limite-20) — o PC Stats usa isso em vez de 70/90 fixo. Alerta = acima do limite por `ALERT_HOLD_MS` seguidos. Os valores chegam por `alerts::feed()` (o poll do PC Stats alimenta); com a aba fechada, `alerts::poll()` no loop busca `/stats` em segundo plano via `agent::get` (silencioso, sem desenhar status; 5s, ou 30s se o agente falhar; sem dados há 1min apaga os alertas). `Screen::alerting()` faz o `ScreenManager` piscar o ícone da aba em vermelho (500ms, redesenhando só aquele slot via `drawTab`) e, com `alertJump`, ir pra aba na subida do alerta. Limite novo força `rebuildScreens()` (a cor já desenhada só muda quando o % muda) — e o rebuild volta pra aba em que estava.
- **Rollback de OTA (`src/ota_guard.h`):** o bootloader do arduino-esp32 tem rollback (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`), mas o core marca o app válido sozinho no boot — `main.cpp` sobrescreve `extern "C" bool verifyRollbackLater() { return true; }` pra assumir. Firmware recém-gravado sobe `PENDING_VERIFY`; `otaguard::poll()` confirma (`esp_ota_mark_app_valid_cancel_rollback`) com WiFi conectado + `OTA_VERIFY_MIN_MS` (15s) de loop. Crash/reset antes disso → o bootloader volta pra versão anterior no próximo boot. Pendurado sem resetar → `esp_timer` (fora do loop) chama `esp_ota_mark_app_invalid_rollback_and_reboot` em `OTA_VERIFY_TIMEOUT_MS` (120s). O `esp_app_desc` do Arduino não tem o `FW_VERSION`, então cada slot grava no NVS a versão que rodou nele (`v_app0`/`v_app1`) pra notificação "Update rolled back" dizer qual falhou (uma vez por OTA: `rbnoted`, rearmado em `onUpdated()` no fim de uma OTA bem-sucedida). **Testar mudança nisso** gravando por OTA builds com `-DOTA_TEST_CRASH` (abort no fim do setup) e `-DOTA_TEST_HANG` (laço infinito no setup), com `-DFW_VERSION` distinto em cada. Pegadinha: OTA seguida de abrir o portal de configuração no primeiro boot passa dos 120s e volta a versão.
- **Improv Wi-Fi pela serial (`src/improv.h`):** o instalador web (ESP Web Tools 10.4) oferece "Connect to Wi-Fi" depois de gravar e no botão *Connect* de uma placa já gravada. Protocolo: `"IMPROV"` + versão 1 + tipo + tamanho + dados + checksum (soma de tudo antes); o navegador lê **linha a linha** e só reconhece pacote no início da linha, por isso `improv::send` cerca cada pacote com `'
'`. RPCs: estado (`PROVISIONED` + URL `http://<ip>/` quando conectado), info, scan de redes (um resultado por rede + resultado vazio no fim) e WiFi (estado `PROVISIONING` → `PROVISIONED`+URL, ou erro `UNABLE_TO_CONNECT` + `READY`). O 1º pedido tem só 1s de prazo, então o Improv é atendido desde a tela de boot (`bootSplashWantsSetup`), em todo `waitConnected` e **dentro do portal**, que agora é não bloqueante (`setConfigPortalBlocking(false)` + laço com `wm.process()`/`improv::poll()`, timeout do portal feito no próprio laço). Quem conecta é um handler trocável: no portal derruba o AP e o sobe de novo se falhar; depois do boot (`improvConnectRunning`) volta pra rede anterior se a nova não conectar. No `loop()` a serial é compartilhada com os comandos de uma letra: `serialcmds::poll` passa cada byte por `improv::feed()` antes (pacote com `s`/`n`/`a`/`r` no meio não dispara comando). Testar sem navegador: `tools/improv_test.py --port COM3` (todos os RPCs + rede inexistente, que tem que voltar pra rede atual) e `--boot` (tempo até responder depois do reset; medido ~1,2s).
- **Notificações (`src/notify.h` + `agent/notify.py`):** `POST /api/notify` (JSON ou form) enfileira até 4 (`notify::push`, fila cheia descarta a mais antiga); `notify::poll()` no loop mostra uma por vez num card sobre a área de conteúdo, com barra de tempo (`duration` s, 0 = até tocar) e "+N" da fila. Enquanto mostra, `ScreenManager::setOverlay(true)`: a tela de baixo não roda `update()` e o auto-next pausa (o pisca de alerta da tab bar continua); ao sumir, `manager.redraw()` redesenha a aba. Toque com notificação na tela só dispensa (`dispatchTouch`: backlight → notify → manager). Acorda a tela à noite (`backlight::wake`). Texto UTF-8 vira ASCII (`notify::toAscii`, Latin-1 sem acento). `rebuildScreens()` redesenha o card por cima se tiver um aberto. `agent/notify.py` é stdlib pura, lê `panel.host/password` do config.json, aceita stdin, tenta de novo em erro de conexão.
- **Pegadinha do `theme::drawBar`:** o preenchimento tem 2px de margem do trilho — com `h` ≤ 4 o preenchimento some (0px). Usar `h` ≥ 6.
- **`agent::get` vs `agent::fetch`:** `get` só faz o GET + parse e devolve um `agent::Result`; `fetch` chama `get` e desenha o status no rodapé. Consulta de fundo usa `get`.
- **WiFi sem modem sleep (`WiFi.setSleep(false)` em `wifi_setup.h`):** com o sleep ligado, conexões de entrada da interface web/OTA se perdiam (sinal fraco piora).
- **Pegadinha resolvida — RST na interface web logo depois de um fetch do agente:** no arduino-esp32 2.0.x, `WiFiClient::connected()` faz `recv()` de 0 bytes (que não define `errno`) e decide pelo `errno` GLOBAL. Um `ENOTCONN`/`ECONNRESET` que sobrou do `HTTPClient` (o agente fecha a conexão) fazia o `WebServer` achar que o cliente novo tinha caído e fechar o socket com o pedido não lido → RST (~4% dos requests na aba PC, sempre colado no poll de 2s). Correção: `errno = 0` logo antes de `server.handleClient()` em `webui::poll()` — não remover. Medido depois: 0 falhas em 600 requests. Qualquer outro código que atenda conexões de entrada (servidor novo, socket próprio) precisa do mesmo cuidado.
- **JS da página da interface web:** carrega tudo em SEQUÊNCIA (css → settings → status → screenshot) e com retentativa (`getJson`, `css()`): o WebServer atende uma conexão por vez e às vezes reseta uma — rajada de requests em paralelo fazia o `/theme.css` falhar e a página não trocar de tema.
- **Interface web + OTA (`src/web_ui.h`):** `WebServer` na porta 80 + mDNS `cyd-dashboard.local`, iniciado no fim do `setup()` e atendido em `webui::poll()` no `loop()`. Página única embutida (PROGMEM) + API JSON. Configurações passam por `settings::setField/getField` (MESMA validação do portal — chave nova vai na lista `settings::KEYS`, no `setField`/`getField`, no `FIELDS` do `wifi_setup.h` e no formulário do `PAGE`). Depois de salvar, `applySettings()` em `main.cpp` aplica na hora; abas/idioma/rotação/inversão recriam as telas (`rebuildScreens`). OTA em `/api/update`: recusa imagem que não começa com o magic `0xE9` (o binário merged do instalador começa com 0xFF e quebraria o boot), mostra progresso no display e reinicia. Senha opcional (`settings.webPass`, HTTP Basic, usuário `admin`).
- **Telas:** `ENABLE_SCREEN_*` (compilação) decide se a tela existe no firmware; `main.cpp` instancia cada uma dentro de `#if` e lista em `allScreens[]` com um id (`clock`, `pcstats`, `procs`, `sysinfo`, `quotes`, `youtube`). Quais aparecem e em que ordem vem da lista `settings.screens` (portal; default `SCREEN_ORDER`) — `registerScreens()` ignora id desconhecido/repetido e, se nada sobrar, mostra todas. A primeira da lista é a aba inicial.
- **`src/screens.h`** define o contrato `Screen` (`name`/`accentColor`/`drawIcon`/`onEnter`/`update`/`onTouch`) e o `ScreenManager` (tab bar fixa no topo + navegação por toque na aba). Telas são registradas em `main.cpp` com `manager.add(&tela)`.
- **`src/theme.h`** — temas/paletas em RGB565 (macros `THEME_*`), constantes de layout (`TAB_BAR_H`, `CONTENT_TOP`, etc.) e os ícones vetoriais/widgets compartilhados (`theme::iconCpu`, `theme::drawBar`, `theme::drawPctBadge`, `theme::drawStatusDot`...). Toda tela nova deve puxar cor e widgets daqui, não usar `TFT_*` cru.

## Tema visual

- **Paleta e temas:** cores via macros `THEME_BG`, `THEME_FG`, `THEME_CURRENT`, `THEME_CARD`, `THEME_COMMENT`, `THEME_CYAN/GREEN/ORANGE/PINK/PURPLE/RED/YELLOW`, que leem a paleta ATUAL em tempo de execução (`theme::pal()`). Temas em `theme::PALETTES_HEX` (hex, convertido pra RGB565 com `theme::rgb()` uma vez por `setTheme()`; o hex fica guardado pra interface web servir `/theme.css` com as cores exatas e `color-scheme` light/dark — a página aplica por cima dos defaults do `<style>` e recarrega o CSS depois de salvar): dracula (default), nord, gruvbox, mocha, tokyonight e latte (claro) — mesma ordem de `settings::THEME_NAMES` (static_assert no tamanho). `settings.theme` (portal/web/`THEME`) → `theme::setTheme()` no boot e no `applySettings()`, que recria/redesenha as telas. Nunca usar `TFT_*` do TFT_eSPI nem RGB565 cru — sempre `THEME_*`, senão a cor não troca com o tema. Como os macros não são constantes, não usar em `static const`/`case`/inicializador global (argumento default de função pode, é avaliado na chamada). Tema novo = entrada em `PALETTES_HEX` + nome em `THEME_NAMES` + `<option>` no `<select>` da `web_ui.h` + README; testar o tema claro com cuidado (texto `THEME_BG` sobre acento fica claro).
- **Desenho sem flicker via sprite (`theme::Canvas`):** todo elemento dinâmico (texto que atualiza, barra, anel, badge, sparkline) é desenhado num `TFT_eSprite` compartilhado e enviado com um único `pushSprite` — atualização atômica, zero piscada. O padrão é create/push/delete por uso (os tamanhos se repetem a cada ciclo, o heap estabiliza; nada de sprite gigante permanente disputando RAM com o WiFi). `theme::drawValue(tft, x, y, w, h, texto, fonte, cor, bg, datum)` substitui o padrão antigo de `setTextPadding` + `drawString` direto para valores dinâmicos — a região inteira (w×h) é redesenhada no sprite, então o valor antigo some junto. **Sempre passar o `bg` real de onde o widget está** (`THEME_BG` ou `THEME_CARD`). **Pegadinha de altura (bug já corrigido uma vez):** se `h` for menor que a altura da fonte (font 4 = 26px), texto centralizado estoura o topo do sprite e os dígitos saem decapitados — por isso o `drawValue` ancora o texto pelo topo quando `fontHeight > h` (cortar por baixo é invisível pra números, é área de descender). Mesmo assim, prefira `h` ≥ altura da fonte quando o layout permitir (font 4 → h=22-26).
- **Navegação por abas:** `ScreenManager` desenha uma tab bar de `TAB_BAR_H`=34px no topo com o ícone de cada `Screen` (via `drawIcon`). A aba ativa vira da cor do conteúdo (`THEME_BG`, efeito "aba conectada") com uma barrinha de destaque (`accentColor()` daquela tela) por baixo; as inativas ficam com ícone em `THEME_COMMENT` sobre fundo `THEME_CURRENT`. Tocar em qualquer ponto com `y < TAB_BAR_H` troca de aba direto (calcula o índice pela posição x); toque abaixo disso vai pro `onTouch` da tela ativa. Não tem mais swipe nas bordas — cada tela é acessada diretamente pela aba.
- **Auto-next:** o `ScreenManager` troca de aba sozinho a cada `settings.autoNextS` (portal; default `AUTO_NEXT_MS`, 10s, via `setAutoNextInterval`) sem interação — dá pra deixar o painel "passando" as telas sozinho. Qualquer toque (numa aba ou no conteúdo) reinicia o timer via `lastActivityMs_`, então não interrompe quem tá mexendo. Intervalo 0 desativa.
- **Ícones são 100% vetoriais** (`theme::iconClock/iconCpu/iconRam/iconDisk/iconNet/iconCoin/iconList/iconPlay/iconArrowUp/iconArrowDown`), desenhados com primitivas do TFT_eSPI (`drawCircle`, `fillTriangle`, etc.) — de propósito, pra não precisar de SPIFFS/LittleFS nem bitmaps embutidos no firmware. Recebem `cx, cy, size, color` — `size=8` é o padrão usado na tab bar; nas linhas de conteúdo usa-se algo maior (11-12) pra ganhar presença visual sem depender de bitmap. Se for adicionar um ícone novo, seguir esse padrão (função livre em `theme.h`, parametrizada por tamanho).
- **Distribuição vertical do conteúdo:** o conteúdo usa a altura toda abaixo da tab bar, não só o topo — evitar layout apertado em cima com vazio embaixo (erro já corrigido uma vez) e **deixar folga real (3px+) entre blocos vizinhos** — bloco encostando em bloco (card terminando na mesma linha y em que a região de texto seguinte começa) parece sobreposição (erro também já corrigido uma vez, no rodapé de rede do PC Stats). PC Stats: anéis CPU/RAM (centro y=90) → sparkline (y=136) → card do disco (y=158, h=36) → rodapé rede (centro y=208) + status (y=231). Cotações: 4 cards de 42px a cada 46px a partir de y=36, status em y=231.
- **Widgets reutilizáveis em `theme.h`:** `drawBar` (barra de progresso arredondada sobre trilho `THEME_CURRENT`), `drawRingGauge` (anel/gauge com `drawSmoothArc`, arco de 30° a 330° com abertura embaixo, valor no centro — usado pra CPU/RAM), `drawSparkline` (mini-gráfico de linha do histórico, valores 0-100 em ordem cronológica), `drawCard` (fundo de card `THEME_CARD` arredondado — estático, desenhado no `onEnter`), `drawPctBadge` (pill verde/vermelho pra variação percentual), `drawStatusDot` (dot colorido + label pequeno pra status de rede/agente). Todos os dinâmicos desenham via `theme::Canvas` (sprite) e recebem um `bg` explícito (a cor que já está por trás) pro blend anti-aliased das bordas — sempre passar a cor de fundo real do local (BG ou CARD), não deixar no default.
- **Smooth font (anti-aliased) nos labels estáticos:** `src/NotoSansBold15.h` é uma fonte suavizada (não é bitmap 1-bit) embutida como array em flash (sem precisar de SPIFFS/LittleFS — segue a mesma filosofia dos ícones vetoriais). Usada via `theme::beginLabelFont(tft)` / `theme::endLabelFont(tft)`, que fazem `tft.loadFont(...)`/`tft.unloadFont()`. **Importante:** enquanto uma smooth font está carregada, ela sobrepõe QUALQUER número de fonte clássica passado a `drawString` (é uma particularidade documentada do TFT_eSPI) — por isso só é usada ao redor de texto estático desenhado uma vez (labels em `onEnter`, data do relógio), nunca em volta de valores que atualizam com frequência (percentual das barras, preço, hora), que continuam nas fontes clássicas rápidas (2/4/6/7/8) com o padrão de `setTextPadding` de sempre. Se for redesenhar algo com smooth font no MESMO lugar depois (não é o caso hoje), lembrar do 3º parâmetro de `setTextColor(fg, bg, true)` — sem ele o fundo não é preenchido e o texto antigo não é apagado.
- **Animações leves, todas via `millis()` sem lib de animação:**
  - Relógio: dois-pontos piscando a cada 500ms (`drawTime` desenha horas, `:` e minutos separados em posições fixas num sprite só — o `:` apagado não desloca os dígitos; redesenha só quando o minuto ou o estado de piscar muda) + barrinha de progresso dos segundos dentro do minuto. 12h (`settings.clockFmt`) põe AM/PM em font 4 alinhado pela base dos dígitos; a data usa `i18n::formatDate` com `settings.dateFmt` (auto/long/dmy/mdy/ymd, sempre com dia da semana).
  - PC Stats: anéis de CPU/RAM e barra do disco fazem *easing* suave até o valor-alvo a cada tick do `loop()` (~20ms, fator 0.3 por tick), redesenhando só quando o percentual inteiro exibido muda. O polling HTTP em si continua no intervalo de `AGENT_POLL_MS`; a animação roda independente disso. O sparkline guarda os últimos 56 polls de CPU (~2 min) em RAM e redesenha a cada poll.
  - Cotações: gráfico de 24h esmaecido atrás do preço (`drawPrice`: sprite único com a linha em `alphaBlend(90, verde/vermelho pela tendência, CARD)` e o preço por cima com `setTextColor(fg)` só, fundo transparente). Escala fixa de `HIST_N`=32 janelas: histórico parcial fica alinhado à direita (horas recentes), senão cards com menos pontos distorcem o tempo. Histórico novo diferente do desenhado zera `lastStr` pra redesenhar.
  - Cotações: preços "rolam" com easing (fator 0.25 por tick) até o valor novo, redesenhando só quando a string formatada muda; o badge de variação só redesenha quando o percentual muda. Ao reentrar na aba, `disp` é igualado ao `target` pra não rolar do zero de novo.
  - Transição de aba: o `ScreenManager` faz um *wipe* — uma linha vertical na cor de destaque da tela nova varre a área de conteúdo (esquerda→direita indo pra frente/dando a volta, direita→esquerda voltando), apagando a tela antiga atrás de si (~100ms, bloqueante via `delay(3)` por fatia).
  - Boot: fade-in do backlight via PWM (`backlight::begin`/`fadeTo` em `src/backlight.h`, canal 0) — a tela acende suave já no fundo do tema em vez de ligar seco.
- **Modo noturno (`src/backlight.h`):** todo controle de backlight passa por esse módulo (nada de `ledcWrite` direto). Entre `nightStart` e `nightEnd` (minutos desde 00:00, no NVS; início == fim desativa; janela pode atravessar a meia-noite) o brilho cai pra `nightBright`. `backlight::update()` reavalia a cada 1s no `loop()`. Com `nightBright` = 0 a tela apaga e `backlight::onTouch()` consome o primeiro toque (só acende, não troca aba) por `NIGHT_WAKE_MS`. Sem hora válida do NTP fica sempre no brilho de dia.
- Cada tela expõe `accentColor()` (cor de identidade daquela aba — Relógio=CYAN, PC Stats=GREEN, Cotações=ORANGE) usada na tab bar e em detalhes do conteúdo (ex.: barra de segundos do relógio usa CYAN).

## Padrão de desenho de tela (importante)

Displays SPI são lentos — **nunca redesenhar a tela inteira em `update()`**. O padrão:

- `onEnter`: desenha o layout estático (cards, ícones, labels) uma vez, direto na tela.
- `update`: atualiza só o que mudou, guardando o último valor em membro (`lastMinute_`, `lastDrawnCpu_`, `drawn_`, etc.) e redesenhando só na mudança.
- Valores dinâmicos são redesenhados via sprite (`theme::drawValue` e os widgets de `theme.h`) — push atômico apaga o valor antigo junto, sem flicker. O padrão antigo de `setTextPadding` só sobrevive em texto estático redesenhado raramente (data do relógio).

Ver `screen_clock.h` (redesenha hora só quando o minuto muda/pisca) e `screen_pcstats.h`/`screen_quotes.h` (poll a cada `AGENT_POLL_MS`/`QUOTES_POLL_MS`, com `drawn_` pra forçar o primeiro desenho e status na base da tela pra erro de rede/agente).

## Adicionar uma tela nova

1. Criar `src/screen_minhatela.h` com uma classe que herda de `Screen`, implementando `name()`, `drawIcon()` (ícone da aba — usar/criar um helper em `theme.h`), `onEnter()`, `update()` e opcionalmente `accentColor()` (padrão é `THEME_PINK`).
2. Em `main.cpp`: incluir o header, instanciar global e adicionar `{"minhatela", &minhaTela}` em `allScreens[]` — ambos dentro de `#if ENABLE_SCREEN_MINHATELA` (com default em `config.h`). Incluir o id em `SCREEN_ORDER` no `config.h` (e no texto do campo de abas em `wifi_setup.h`).
2b. Dados do agente: `agent::fetch(tft, "/endpoint", doc)` (`agent_client.h`); textos em `i18n.h` nas duas línguas.
3. Usar sempre as cores/widgets de `theme.h`, nunca `TFT_*` cru — mantém a tela consistente com as outras e faz ela trocar de cor junto com o tema.

## Agente do PC

`agent/pc_stats_agent.py` — servidor HTTP (stdlib + `psutil`) na porta 8377 + anúncio UDP na rede, cinco endpoints (cada um alimentado por uma thread de background própria; o handler HTTP só lê cache):

- `GET /stats` — CPU, RAM, disco (uso % + MB/s leitura/escrita) e rede (MB/s down/up). Rede e disco são medidos por delta em thread de background (`_io_monitor`, a cada `intervals.io`=1s). Vários discos: `disks` no config (`null` = só `disk_path`; `"all"` = partições fixas sem removível/CD, reavaliado a cada 30s; ou lista de paths/`{path, name}`) → `/stats` devolve `disks: [{name, pct, used_gb, total_gb}]` e mantém `disk` (o primeiro) por compatibilidade. No firmware o card do disco do PC Stats alterna entre eles a cada `DISK_CYCLE_MS` (toque no card pula), mostrando o nome no lugar de "DISK" (sprite com smooth font, sem flicker); o alerta de disco usa o mais cheio.
- `GET /quotes` — `{base, prefix, items: [{symbol, price, change_pct}]}` na ordem de `quotes.assets` do config (`price: null` = ainda não buscado; o firmware pula a linha). Buscadas por thread de background (`_quotes_monitor`, a cada `intervals.quotes`=60s) via AwesomeAPI (fiat, par `SYM-BASE`) e CoinGecko (cripto, por `id`), cada fonte falhando de forma independente, cacheadas em memória — o handler HTTP nunca bate na API externa por request. Se o fetch falhar, mantém o último valor conhecido e loga o erro (não derruba a thread).
- **Histórico das cotações (`_quotes_hist`, `history_hours`/`history_points`):** `items[].history` = `history_points` valores igualmente espaçados no TEMPO (`_hist_series`: último preço de cada janela, janela vazia repete a anterior, sem pontos antes do primeiro dado). Seed na subida (`_hist_seed`): CoinGecko `market_chart` (24h em 5 min, 2s entre moedas por causa do rate limit do plano grátis) e AwesomeAPI `/json/{PAR}/100` (esparsa) filtrada às últimas 24h; depois cada poll de 60s acrescenta um ponto. Persistido em `agent/quotes_history.json` (gitignored; descartado se a moeda base mudar), salvo no 1º poll e a cada 10. Todo acesso a `_quotes_hist` sob `_quotes_lock` (thread de cotações escreve, threads HTTP leem).
- `GET /procs` — top `top_procs` (4) processos por CPU, agregados por nome (todos os `chrome.exe` viram uma linha), com RAM somada em MB. `_procs_monitor` a cada `intervals.procs`=3s; CPU normalizada pelo nº de núcleos. Mesma pegadinha do `cpu_percent`: por-processo ele também mede desde a última chamada naquele objeto `Process` — o `process_iter()` cacheia as instâncias, então funciona numa thread única. Filtros: o ocioso do sistema sai sempre; `procs.ignore` (fnmatch case-insensitive, sem `.exe`) e `procs.ignore_self` (default true — esconde o agente pelo PID + o pai se for launcher do Python, já que o Python Install Manager roda launcher + filho) são aplicados ANTES do ranking, então o top 4 é preenchido pelos próximos.
- `GET /sysinfo` — `ping_ms` (TCP connect em `ping.host:ping.port`, default 8.8.8.8:53 — ICMP puro exigiria admin no Windows), `public_ip` (`public_ip_url`, a cada 10min), `uptime_s` e as taxas de rede atuais. `_sys_monitor` a cada `intervals.sysinfo`=5s.
- **Temperatura da CPU (`_temp_monitor`, `temperature` no config):** `/stats` tem `cpu_temp` (°C ou `null`). `source: "auto"` = `psutil.sensors_temperatures` no Linux (drivers `coretemp`/`k10temp`/`zenpower`/`cpu_thermal` primeiro) e LibreHardwareMonitor no Windows (o psutil não lê temperatura lá): GET em `lhm_url` (`data.json` do Remote Web Server, porta 8085), percorrendo a árvore e pegando sensores de temperatura sob hardware de CPU (ícone `cpu.png` ou `SensorId` com `cpu/` — funciona em versões novas e antigas do LHM; GPU/disco ficam de fora). Valor tem `°C` e pode ter vírgula decimal (Windows pt-BR). Preferência: package/tctl/tdie/core average/core max, senão o núcleo mais quente; `temperature.sensor` força por nome. Sem fonte: loga uma vez e tenta de novo a cada 30s. No firmware, `alerts::TEMP` (limite `settings.alertTemp`, °C, default 85; `feed()` recebe `NAN` sem fonte) e o PC Stats mostra "61°C" à direita do sparkline (que encolhe; o "°" é um círculo desenhado, as fontes não têm). Testar sem o hardware/LHM: `tools/mock_lhm.py --temp 61.4` (ou `--file` pra mudar a temperatura com ele rodando) + `"lhm_url": "http://127.0.0.1:18085/data.json"` num config de teste.
- **Token (`token` no config ou env `CYDPC_AGENT_TOKEN`, que tem prioridade):** vazio = sem auth (default, compatível). Com token, `StatsHandler._authorized` exige header `X-Agent-Token` (ou `?token=`), comparando com `hmac.compare_digest`; senão 401. O firmware guarda em `settings.agentToken` (chave `token`, nunca devolvida pela API — só `token_set`), manda o header em `agent::fetch` e mostra "bad token" no 401. O anúncio de descoberta leva só `"auth": true/false`.
- **Descoberta (`_discovery_beacon`):** não é endpoint — broadcast UDP `{"cydpc": 1, "port", "name"}` a cada `discovery.interval`=5s pra porta `discovery.port`=8377, no endereço de broadcast DIRECIONADO de cada interface IPv4 ativa (o 255.255.255.255 no Windows sai por uma interface só). Só saída: não precisa regra de firewall. O firmware (`src/discovery.h`) escuta em `DISCOVERY_PORT`; com o IP do agente `auto` (default de `AGENT_HOST`) usa o agente ouvido, e só troca se ele ficar 30s sem anunciar. `agent::fetch` resolve o endereço via `discovery::resolve` (status "finding agent" se nada ouvido). `/api/status` da interface web lista os agentes ouvidos.
- `GET /youtube` — título/inscritos/views/vídeos dos canais em `youtube.channel_ids` via YouTube Data API v3 (`_youtube_monitor`, a cada `intervals.youtube`=30min — 1 unidade de quota por fetch, folgadíssimo). **Requer `youtube.api_key`** no config (ou env `YOUTUBE_API_KEY`, que tem prioridade). Sem chave, responde `{"configured": false}` e a tela mostra o aviso.

**Config do agente:** `agent/config.json` (gitignored; copiar de `config.example.json`), deep-merge sobre `DEFAULT_CONFIG` no topo do script — chave nova = default lá + exemplo no `.example.json` + README. CLI: `--config`, `--port` (útil pra testar sem brigar com o agente já rodando na 8377). `CFG` é global, preenchido em `main()` antes de subir as threads.

Testar no navegador (`http://IP:8377/stats` e `/quotes`) antes de suspeitar do ESP32. Porta 8377 precisa estar liberada no firewall (rede privada). Sem novas dependências pip — `urllib` é da stdlib.

**Pegadinha resolvida — `psutil.cpu_percent(interval=None)` é por-thread:** ele mede o uso desde a *última chamada feita naquela mesma thread*. O `ThreadingHTTPServer` cria uma thread nova a cada request, então chamar `cpu_percent` direto no handler faz cada request parecer "a primeira chamada" — sempre retorna 0.0. Por isso o CPU é medido dentro do `_io_monitor` (thread única e persistente) e cacheado em `_io_state["cpu_pct"]`; o handler só lê o cache. Se for adicionar qualquer outra métrica baseada em delta/estado interno do psutil, medir na thread de background, nunca no handler.

**Nota de dev (Windows + Git Bash):** rodar `python pc_stats_agent.py &` no Git Bash pode deixar processos zumbis presos na porta 8377 (o `HTTPServer`/`ThreadingHTTPServer` do Python tem `allow_reuse_address=True` por padrão, então o Windows deixa múltiplos processos "escutarem" a mesma porta sem erro, e as respostas saem de qualquer um deles). Se o `/stats` parecer não refletir mudanças no código, cheque `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` e mate processos `pc_stats_agent.py` duplicados antes de reiniciar.

**Autostart (Windows):** `agent/install_autostart.ps1`/`.bat` registra a tarefa "CYD PC Dashboard Agent" no Agendador (logon, `pythonw` + `--log agent.log`, sem admin); `uninstall_autostart` remove. O `stop`/`restart` matam `python.exe` E `pythonw.exe`. Com o Python Install Manager aparecem 2 processos `pythonw` (launcher + filho) — é uma instância só.

**Scripts de conveniência:** `agent/start_agent.bat` / `stop_agent.bat` / `restart_agent.bat` (duplo-clique no Windows) automatizam exatamente essa checagem/limpeza — `start` não duplica se já tem algo na porta 8377, `stop` mata todo processo cujo command line contenha `pc_stats_agent.py` (não só um PID, por causa da questão dos zumbis acima). O agente é um processo manual, não sobrevive a reboot — não tem serviço/agendador configurado por padrão. **Os `.bat` terminam com `pause`** — rodá-los de uma sessão não-interativa (agente de IA, CI) trava no final; nesse caso, iniciar o agente direto com `Start-Process python .../pc_stats_agent.py` redirecionando stdout/stderr pra log.

**Pegadinha de teste (Git Bash + `cmd.exe`):** ao testar esses `.bat` via Git Bash, `cmd.exe /c arquivo.bat` falha silenciosamente — o MSYS converte `/c` num path estilo Windows antes de repassar. Usar `cmd.exe //c arquivo.bat` (barra dupla) pra escapar, mesmo truque já usado com `taskkill //F //PID`. Isso é só uma pegadinha do ambiente de teste via Git Bash — não afeta o usuário final, que dá duplo-clique no `.bat` direto no Explorer.
